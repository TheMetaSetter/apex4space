# Web data package

Generated by `python3 tools/build_web_data.py`. The script streams the four
quality-controlled sensor files and writes compact calendar data plus a
date-specific GeoJSON map sample. It does not rewrite source or processed CSVs.

The event-harmonized activity products are generated by
`python3 tools/harmonize_hotspot_clusters.py`.

## Files

- `calendar_monthly_by_sensor.json` — one row per month, sensor/platform,
  archive or NRT product, source version, and FIRMS fire type. Use this for
  calendar charts and sensor/source filters.
- `hotspots_YYYY-MM-DD.geojson` — individual observations for the requested
  UTC date. The default sample is `hotspots_2023-07-12.geojson`. Use its
  features to test map rendering and popups.
- `data_manifest.json` — input row counts, rows included/skipped, output
  counts, date and processing scope.
- `event_calendar_monthly.json` — monthly activity measured as unique
  1 km equal-area cell-days, with raw observation and per-satellite totals,
  fire-type categories, and a Terra-only baseline.
- `hotspot_cell_days_YYYY-MM-DD.geojson` — one point per active grid cell on
  the selected UTC date, with sensor-specific counts and FRP maxima.
- `event_harmonization_manifest.json` — cell size/projection, input counts,
  exclusions, overlap counts and interpretation.

## Observation fields

GeoJSON feature properties include:

| Field | Meaning |
|---|---|
| `latitude`, `longitude` | FIRMS point coordinates in decimal degrees |
| `frp` | Fire Radiative Power value as provided in the normalized FIRMS data |
| `datetime_utc` | Acquisition timestamp in UTC |
| `sensor`, `satellite` | MODIS/VIIRS instrument family and platform |
| `confidence_original` | Original MODIS numeric or VIIRS categorical confidence |
| `confidence_score_heuristic` | Existing convenience mapping; not a probability or calibrated cross-sensor score |
| `fire_type`, `fire_type_label` | Source fire-type code and readable label; NRT records may have no type |
| `product_type`, `version` | Archive/NRT provenance and source product version |
| `record_id` | Source file plus source row number for traceability |

GeoJSON coordinate order is `[longitude, latitude]`.

## Event harmonization definition

The operational calendar unit is a **1 km equal-area cell on one UTC day**.
Coordinates are projected for indexing with `x = R * longitude_radians` and
`y = R * sin(latitude_radians)`, where `R = 6371.0088 km`; integer kilometre
indices define the cell. All sensor detections in the same cell-day contribute
to one activity unit. This removes repeated same-cell/day observations from
the activity-unit count while retaining their counts and source-specific
measurements.

A cell-day with MODIS and VIIRS observations is counted as
`multi_sensor_cell_days`. MODIS and VIIRS detections, FRP maxima, confidence
categories, product versions, and fire-type codes remain available separately
in the map properties or monthly satellite fields. Missing fire type remains
unknown. No synthetic common confidence score is used by the cell-day output.

This is a spatial-temporal aggregation for a burning-activity calendar, **not
a count of unique fires**. Multiple fires can occur in one cell on the same
day; one fire can also span adjacent cells or days. FRP maxima remain per
satellite and are not calibrated across sensors.

## Calendar fields

Each monthly record includes `detections`, `frp_sum`, `frp_mean`, `frp_min`,
and `frp_max`, grouped by month, sensor, platform, archive/NRT, version, and
fire type. These summarize **detections**, not unique fires. FRP aggregates
remain stratified by sensor/platform; do not add MODIS and VIIRS values and
present the result as a calibrated common measure.

For an event-harmonized calendar use `event_calendar_monthly.json` instead.
Its `hotspot_cell_days` counts the grid-day activity units above;
`multi_sensor_cell_days`, `MODIS_only_cell_days`, and `VIIRS_only_cell_days`
partition those units by which sensor families observed them. The observation
totals remain available so the UI can show the difference between raw
detections and harmonized activity units. `terra_backbone_cell_days` counts
cell-days with Terra detections and is the recommended long-running
platform-specific trend line. `hotspot_cell_days` is the all-sensor spatial
union and can change as sensors are added or removed.

The event calendar also has mutually exclusive cell-day classes:
`vegetation_type_only_cell_days`, `other_known_type_only_cell_days`,
`unknown_type_only_cell_days`, and `mixed_or_partly_unknown_type_cell_days`.
Type 0 means *presumed* vegetation fire; codes 1-3 are other known source
classes. NRT rows with no type stay unknown. Do not count mixed/unknown
cell-days as confirmed vegetation fires.

## Web integration notes

- The full 84.9-million-row source is not intended to be downloaded by a
  browser. Use a backend or database to query selected AOIs/date ranges.
- The monthly JSON supports the whole current South America dataset. The
  GeoJSON is only a point-map sample for one date; rerun with
  `python3 tools/build_web_data.py --map-date YYYY-MM-DD` to create another
  date sample (the script re-reads all input files).
- `event_calendar_monthly.json` covers every month present in the input. The
  cell-day GeoJSON is a map sample for one date; rerun
  `python3 tools/harmonize_hotspot_clusters.py --map-date YYYY-MM-DD` to export
  another date. For an interactive map, the backend should query/index the
  source observations and return cell-days for the selected date and AOI.
- The cell-day layer aggregates observations by common area and UTC date, while
  retaining per-sensor counts and FRP summaries. It does not identify unique
  fires/incidents and does not scientifically calibrate FRP or confidence
  between sensors.
- Archive and NRT rows are both present and distinguished by `product_type`;
  treat the most recent NRT period as provisional.
